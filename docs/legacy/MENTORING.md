# 能力验证与面试证据

本次已由 agent 完成代码、回归执行和工程说明。下面的用户现场任务目前均是**待完成**；提交命令输出、解释和 diff 后才更新能力状态。不要把“读过文档”或“agent 测试通过”写成独立掌握。

## 现场 1：Python async / HTTP SSE（约 25 分钟）

从当前分支新建自己的练习分支。先运行 README 的离线测试，再运行慢流探针，保存自己的报告而不覆盖已有 before/after 证据。

用自己的话逐行解释 `chat.py` 的 event_stream 与 `llm_client.py` 的 achat_stream：等待发生在哪里、谁负责取消、finally 在正常结束/异常/断连分别何时执行。指出原普通 for 为什么会卡住健康检查。

提交：自己的测试输出、探针 JSON、对 `sse-before.json` 中负 cancel-to-close 数字的解释。追问：SSE 接口收到 HTTP200 后为何还可能发生业务错误？心跳是否等于有效回答？

## 现场 2：小改动 + 排错（约 25 分钟）

在自己的分支给空流切换增加一条结构化日志，记录 provider、reason=empty_stream、emitted；不能记录 API Key、完整 prompt 或游客隐私。自己补一项 caplog 测试，证明空白流会打日志，正常有效文本不会误打。

先做一个故意把 emitted 放在空白过滤之前的错误版本，运行最小回归观察失败，再修正；保留失败输出与最终 diff。不要修改正式交付分支，也不要仅复制现成测试答案。

提交：一个小 commit、测试先红后绿、解释“输出后的空格为什么仍需保留”。验收者应当能只看 diff 判断行为改变。

## 现场 3：SQL 事务与缓存（约 30 分钟）

在临时 SQLite 文件迁移至 head，查询 `select * from knowledge_revision`。运行知识 HTTP 回归并观察新增、切块、索引、删除前后的版本变化。另开连接演示一个写事务回滚后内容和版本都不变。

解释 RLock 与数据库 revision 各解决什么问题；画出“旧查询开始→新知识提交→旧查询返回→新查询开始”的四步顺序，指出旧查询缓存键为何不能覆盖新版本。

提交：实际 SQL 输出、失败事务输出、一个自己补充的不同数据库缓存隔离测试。不能把“SQLite 测试通过”外推为 PostgreSQL 已验收。

## 现场 4：Git 协作 / CI / 部署（约 30 分钟）

用 git status、git diff、git diff --check 说明自己修改了什么；确认基准 SHA，解释工作区、暂存区、commit 和远端分支的差异。只提交自己的练习文件，避免夹带别人的修改。

审阅 backend-regression.yml：解释为何没有 services/模型密钥、matrix 测了哪些组合、JUnit 保留什么证据。待决定推送后亲自查看一次 GitHub Actions，保存运行链接；配置文件存在本身不代表 CI 成功。

按工程说明启动自己本地的数据库和后端，实际访问 /health，再发送 /api/chat/stream 并观察事件。知识为空时应说明原因，不从旧报告复制答案。说明默认生产 Compose 的 PostgreSQL 与测试 SQLite 的差别。

提交：自己的 commit SHA、CI 链接、健康检查/流式事件输出与启动时遇到的问题及解决过程。

## 当前可用与条件性简历表达

当前事实：原仓库有 RAG、多模型客户端、ASR/TTS 和数字人界面；agent 在独立分支修复三个可靠性问题并实际运行离线测试。用户个人完成情况未验证。代码助手实验尚未开始，没有成功率/成本结论。

在完成上述现场任务后，可按实际参与范围改写为：

> 在 AI 辅助下维护开源景区导览系统，复现并修复文本 SSE 同步 I/O 阻塞、空流容错遗漏及知识更新后的检索缓存问题；使用模型替身和临时数据库补充并执行回归，配置无真实外部服务的 CI，并通过可审查 diff 与时序记录验证行为。

只有自己真正设计、修改并解释过对应部分，才把“在 AI 辅助下验证”升级为“设计并实现”。只有远端 Actions 运行成功后才写“接入并验证 CI”。不写独立研发整个系统、生产高并发、问答准确率提升或 Agent 成功率提升。

岗位能力映射：AI 应用关注检索/模型/边界与评测；Agent 关注工具权限、反馈循环与验收隔离；AI Coding 关注故障定位、补丁与回归；研发效能关注可重复脚本、CI、证据和协作。先用本项目验证缺口，再决定是否新增项目。
